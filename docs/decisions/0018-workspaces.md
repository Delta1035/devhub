# 0018 工作区：扫描目录并自动同步项目

- 状态：已采纳
- 日期：2026-10-04

## 背景

代码目录里常有几十个仓库，逐个「添加项目」很繁琐，新建或删除的仓库也不会反映到 DevHub。用户在「一次性导入」与「持续关联的工作区」之间选择了工作区：记住一个目录，自动发现其中的项目并保持同步；默认只扫描直接子目录，可设 1～5 层；JS monorepo 子包暂不展开。

## 决策

- **发现的项目存为普通项目**：`Project` 增加可选 `workspaceId`，仍存于 `projects.json`（版本不变，旧文件无需迁移）。批量任务、运行历史和日志都按 `projectId` 关联，必须保持 id 稳定，所以不在每次扫描时临时生成。工作区存于 `workspaces.json`：路径、层数、已排除路径。
- **判定项目**：目录中有探测器读取的构建文件（`package.json`、`pom.xml`、`build.gradle(.kts)`、`settings.gradle(.kts)`、`.devhub.yaml/.yml`）。只有 `.git` 不算。找到项目后不再深入（Maven / Gradle 子模块由根项目展开，见 ADR 0013）；根目录本身不算项目。
- **扫描边界**：跳过隐藏目录、`node_modules`、`target`、`build`、`dist`、`out`、`vendor` 及 Windows 系统目录；不跟随符号链接与 junction（也杜绝循环）；最多读取 5000 个目录。根目录不可读返回「不可用」，子目录读取失败或触及上限时结果标记为不完整。用 Node 自带 `fs.readdir`，无新依赖。
- **同步规则**（`workspace-sync.ts` 纯函数）：移除项目会清理其历史，因此偏向保留。
  - 新发现的目录自动添加；已作为项目存在的目录（手动添加或属于其他工作区）不重复添加。
  - 目录已被删除的项目保留，显示为现有的「目录缺失」，由用户移除——切换分支或拔掉移动硬盘不应清空历史。
  - 扫描不完整、根目录不可用、项目仍有运行时，不移除任何项目。
  - 目录存在但不再符合条件（调低层数、删除构建文件）则移除。
  - 已排除的路径始终移除。
- **排除**：从侧栏移除工作区内的任一项目（包括位于工作区目录中的手动项目）时，把路径记入该工作区 `excluded`，以后的扫描不再加回；可在工作区设置中恢复。
- **工作区之间不得互相包含**，避免同一目录归属两个工作区。移除工作区连带移除其项目与历史（界面二次确认）。
- **扫描时机**：应用启动时后台扫描一次；renderer 的工作区查询本身调用 `rescanWorkspaces`，因此挂载与窗口聚焦时重扫；另有手动重扫按钮。core 中所有工作区操作串行执行，并发的重扫请求合并为一次。只有项目或扫描结果（可用性、完整性、警告）变化时才推送 `projects-updated`，renderer 收到后重新读取列表，不再触发扫描，避免循环。
- **API**：`listWorkspaces` / `addWorkspace` / `updateWorkspace` / `removeWorkspace` / `rescanWorkspaces`，走现有自动 IPC 映射；输入在 core 用 zod 校验。

## 备选与理由

- **一次性导入**：改动小，但不能自动跟随新增 / 删除的仓库，用户明确选择了持续同步。
- **文件系统实时监听**：需要新依赖（chokidar 等），跨平台行为差异与资源占用大；聚焦时重扫已足够及时。
- **扫描时临时生成项目、不持久化**：项目 id 不稳定，批量任务与历史会失去关联。
- **目录消失即自动移除**：会因临时不可用（分支切换、网络盘断开）误删历史，故改为显示缺失、交给用户。

## 验证与限制

单元测试覆盖扫描（层数、跳过目录、junction 循环、读取失败、上限）、同步规则的每种情况、Windows 路径大小写、排除与恢复、重叠拒绝、并发重扫合并；E2E 覆盖添加、磁盘变化后重扫、排除恢复、调层数、关闭期间新增的项目在重启后出现、移除工作区。Windows 与 Linux 均通过。

不展开 JS monorepo 子包；判定只看构建文件，不识别其他语言项目。`excluded` 中已不存在的路径不会自动清理。
