# 0011 健康检查

- 状态：已采纳
- 日期：2026-10-03

## 背景

脚本「运行中」不代表服务可用：Spring Boot 要几十秒才能接受请求，前端开发服务器可能编译失败但进程仍在。用户需要知道服务什么时候真正就绪、运行中是否失去响应。批量执行原有的「端口可连接」条件也不够：端口打开时应用可能还在初始化。

## 决策

### 检查什么

支持 `ports`、`http`、`output`、`alive` 四种多模态健康检查探针，按以下规则确定检查目标：

- **显式探针配置**（`.devhub.yaml` 中的 `health` 对象）：
  - `ports`（`{ type: 'ports', ports: number[] }`）：指定的端口全部能连上即为就绪。
  - `http`（`{ type: 'http', path: string, port?: number }`）：请求 `http://localhost:<port 或第一个端口><path>`，返回 2xx 才算就绪；不跟随重定向（跳到登录页不算健康）。未指定 `port` 且脚本无已知端口时，配置报错。
  - `output`（`{ type: 'output', pattern: string, regex?: boolean }`）：进程输出包含 `pattern`（`regex: true` 时按正则匹配）即为就绪。
  - `alive`（`{ type: 'alive', delayMs?: number }`）：进程保持运行且启动后稳定存活达到 `delayMs`（默认 `2000` ms，范围 500～30000 ms）即为就绪。
- **有已知或推断端口时**（`Script.ports`，与启动前端口冲突检测共用）：
  - 若 `.devhub.yaml` 中写了路径字符串 `health: /actuator/health`，改为在第一个端口上做 `http` 检查；写了该字段却无法确定端口时，配置报错。
  - 否则默认做 `ports` 检查：全部端口能连上即为就绪。只看端口时**不发 HTTP 请求**，避免数据库、gRPC 等非 HTTP 服务被误判。
- **未显式配置端口或探针的脚本**：默认应用 `alive` 检测（`delayMs: 2000`），即启动后稳定存活 2 秒即标记为就绪，不再跳过检查。

### 状态与节奏

- `starting` → 首次检查成功 → `ready`；之后连续 3 次失败 → `unhealthy`；再次成功回到 `ready`。
- 启动中每 1 秒检查，就绪 / 无响应后每 5 秒检查；启动中没有超时（大型后端可能启动很久）。
- 运行进入「停止中」、退出或被移除时立即停止检查。

### 结构

- `core/health/health-monitor.ts` 订阅运行事件，独立于 `RunManager`；检查目标经 `scripts.find` 现查（与启动脚本一致，不缓存）。不依赖 Electron，远程端可直接复用。
- 健康状态不放进 `Run`：新增事件 `run-health`（`health` 为 null 表示不再检查）与 API `listRunHealth()`（刷新页面后恢复）。进程状态与就绪状态变化频率和来源不同，分开避免互相覆盖。
- HTTP 检查用 Node 自带的 `fetch`（`core/net/http-check.ts`），同时尝试 127.0.0.1 与 ::1，超时 2 秒。无新依赖。

### 界面与批量执行

- 脚本行徽标：启动中（琥珀）/ 就绪（绿）/ 无响应（红），悬停显示检查目标；终端标签圆点同色。
- 批量执行新增继续条件「HTTP 返回成功」：任意 http / https 地址，返回 2xx 即继续（每 0.5 秒检查，带超时）。

## 备选与理由

- 把健康状态加进 `Run`：每次检查结果都要经 RunManager 改写运行记录，耦合进程管理与网络检查。
- 端口推断出的脚本也默认请求 `/`：很多服务对 `/` 返回 404 或根本不是 HTTP，误报多。
- 启动中设超时并转为「无响应」：启动时长差异太大，难以给出合理默认值；继续显示「启动中」更诚实。

## 已知限制

- 端口靠推断：脚本里没写端口、也不是已知工具时仅默认应用 `alive` 存活检测，可在 `.devhub.yaml` 中写 `port` 或显式配置 `health` 探针。
- 端口被其他进程占用时（用户选择了「仍然启动」），端口检查会连到那个进程，显示为就绪。
